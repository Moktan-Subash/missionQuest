## Core Concept
MissionQuest (formerly esports missions) is a platform that allows casual and semi-pro gamers to monetize their gaming time and talent by completing specific in-game challenges ("missions") for real cash, coupons, or rewards.

---

## PHASE 1: Core Mission & Reward (Current Focus)
We are focusing exclusively on the core mission and reward loop for the first release.

### 1. User Authentication & Profile
- Sign up and login using email/password (via Supabase Auth).
- Profile creation: username, email, list of gaming usernames/IDs (e.g., MLBB Ign, PUBG character ID).

### 2. Mission Board
- Users can browse a list of active missions.
- Each mission displays:
  - Game Name (e.g., Mobile Legends, PUBG Mobile)
  - Mission Description (e.g., "Get 15 kills in a Classic Match", "Get MVP in a Ranked Match")
  - Reward Amount (e.g., Rs. 50 / $0.50)
  - Rules & Requirements (e.g., Must show match date, score, and username clearly)

### 3. Mission Submission & Verification
- When a user wants to claim a reward:
  - They select the mission.
  - They upload a screenshot of their end-game scoreboard as proof of completion.
  - Submission status: `Pending Review` -> `Approved` or `Rejected` (with reason).
  - *Verification plan:* Start with manual admin verification (via a dashboard/Supabase), with plans to introduce AI screenshot scanning (Gemini) to automate approval.

### 4. Wallet & Withdrawal System
- Users have a virtual wallet tracking their earnings.
- When a mission is `Approved`, cash is credited to their wallet balance.
- **Withdrawal integration:**
  - Local market: **eSewa** (Nepal)
  - International market: **PayPal**
  - Users request a payout -> admin processes withdrawal.

## DATABASE SCHEMA DESIGN (Supabase)
To support Phase 1, we will need the following database tables:

1. **profiles**
   - `id` (references auth.users)
   - `username` (text)
   - `game_ids` (jsonb: map of game names to user's in-game names/IDs)
   - `created_at` (timestamp)

2. **missions**
   - `id` (uuid)
   - `title` (text)
   - `description` (text)
   - `game` (text: e.g., 'MLBB', 'PUBG')
   - `reward_amount` (numeric)
   - `rules` (text)
   - `is_active` (boolean)
   - `created_at` (timestamp)

3. **submissions**
   - `id` (uuid)
   - `user_id` (references profiles)
   - `mission_id` (references missions)
   - `screenshot_url` (text: path to uploaded image in Supabase Storage)
   - `status` (text: 'pending', 'approved', 'rejected')
   - `rejection_reason` (text)
   - `submitted_at` (timestamp)

4. **wallets**
   - `id` (uuid, references profiles)
   - `balance` (numeric)
   - `updated_at` (timestamp)

5. **payout_requests**
   - `id` (uuid)
   - `user_id` (references profiles)
   - `amount` (numeric)
   - `payment_method` (text: 'esewa', 'paypal')
   - `payment_details` (text: phone number or email)
   - `status` (text: 'pending', 'processed', 'cancelled')
   - `requested_at` (timestamp)

### 3. Real Payment Integration (replaces manual-send + admin-verifies-screenshot)
- eSewa (Nepal) and PayPal: client kicks off checkout -> provider confirms -> a Supabase

  trust the client saying "payment succeeded").
- That Edge Function then calls a `SECURITY DEFINER` Postgres RPC to credit the wallet /
  upgrade membership — same atomic, race-safe pattern already used by
  `start_mission_attempt()` in schema.sql.
- Decide whether to keep manual verification as a fallback (e.g. for large amounts) or
  fully replace it once the automated flow is live.
- Both providers also send server-to-server webhooks on payment completion — need a public
  endpoint for those too; Edge Functions get one automatically.
